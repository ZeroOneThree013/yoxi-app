# yoxi AI 出行夥伴 — 產品規格交接文件

> 本文件整理自互動原型 `yoxi-app-flow.html`（純前端、假資料、可點擊）的所有定案功能決策，
> 提供給 Claude Code 作為實作與部署的依據。原型檔案本身可以直接丟給 Claude Code 當作
> UI／互動流程的視覺與行為參考，但**不要**直接把原型的程式碼當成正式架構沿用——
> 它是用單一 HTML 檔、假資料、DOM 操作寫的展示品，正式開發需要重新用框架實作。

---

## 1. 產品定位

yoxi 從單純的叫車 App，延伸成「AI 出行夥伴」：不只是搭車前才打開，而是平常就會用來
收藏想去的地方、被動接收 AI 推薦任務、累積徽章與點亮個人城市地圖。核心迴圈：

```
每日互動（十秒問答）→ 收藏地點（截圖存地點）→ AI Agent 規劃路線
→ 出發與轉換（叫車 / 餐廳訂位）→ 任務獎勵（徽章 + 地圖點亮）→ 回到每日互動
```

## 2. 使用者流程與畫面清單

### 2.1 Onboarding（首次開啟，共 3 步）
1. 基本資料：暱稱、常出沒城市
2. 一週有空時段：星期（複選 chip）、常見時段（複選 chip，如「晚上下班後」「午休」「週末整天」）
3. 十秒問答：心情（單選 emoji）、想去的方向（單選：山／海／城市／巷弄裡）、出走指數（1–10 滑桿）

> 十秒問答**不是只在 onboarding 做一次**，首頁也有「每日互動」入口可以重新填寫，
> 每次填寫結果應作為當次 AI 推薦的偏好參數（口味、心情、活動半徑等）。

### 2.2 首頁（5 個入口卡片）
1. **每日互動** — 進入十秒問答
2. **每日任務** — 進入任務選單（見 2.3）
3. **想去的地方** — 收藏地點清單（見 2.4）
4. **AI Agent** — 多選收藏地點 → AI 規劃路線（見 2.5）
5. **單純叫車** — 不算任務的純叫車入口（見 2.7）

### 2.3 每日任務（**沒有積分／連續打卡機制**，改為徽章＋地圖點亮）
- **任務一・今日推薦任務**：AI 依使用者有空時段，不定時推送小任務
  （例：「11:00–15:00 完成一趟咖啡廳行程」）。沒有連續天數壓力，錯過會在下次有空檔時再推薦。
- **任務二・節氣・季節限定地點**：收藏地點若符合節氣／季節限定條件
  （例：夏至剉冰店、冬至湯圓店），實際造訪後解鎖對應徽章，累積在個人徽章牆。

### 2.4 想去的地方（核心收藏功能）
- 地點來源：使用者截圖 IG／Facebook／Google Maps 的畫面，上傳到 App
- 後端流程：截圖 → VLM 圖片轉文字 → （條件觸發）OCR 輔助 → 關鍵字擷取
  → 必須存出「地點（可能是地區，如台南）」與「種類（如咖啡廳，用於推薦偏好）」
- **前端呈現原則**：上傳後直接顯示「可編輯的辨識結果」欄位（地點／店名／種類／來源），
  一步到位，**不需要**呈現 OCR 介入的中間畫面或提示——OCR 是後端條件觸發的輔助機制，
  使用者不會意識到它的存在。
- 使用者可編輯辨識結果後儲存，存入收藏清單。

### 2.5 AI Agent 路線規劃
- 入口：從「想去的地方」或首頁 AI Agent 卡片進入「選擇任務地點」畫面
- 地點來源分兩種（Segment 切換）：
  1. **已存未去**：使用者收藏但還沒去過的地點
  2. **依偏好推薦**：依關鍵字種類（咖啡廳／逛街等）+ 十秒問答偏好推薦的地點
- **可複選多個地點**（不是單選）
- 選完後，AI 依目前 GPS 位置規劃「最佳造訪順序」與路線
- 地圖呈現：**真實地圖**（Leaflet.js + OpenStreetMap 圖資，marker 依造訪順序編號，
  點擊跳出地點名稱／類型小卡片；地點之間用 OSRM 規劃貼合道路的真實路徑，
  OSRM 失敗時 fallback 同色直線，不可讓畫面空白）
- 統計卡片：總公里數、預估車程分鐘、預估車資

### 2.6 出發與轉換（路線規劃完成後的分支）
規劃完成後，使用者可以選擇兩種方式完成這趟行程，**兩條路徑最終都會走到「任務獎勵」**：
1. **叫 yoxi 前往**：一般叫車
2. **餐廳訂位（跨界合作）**：與合作餐廳的訂位流程（例：保留座位、到店時間）

### 2.7 單純叫車（不算任務，維持獨立）
- 給只想搭車、不想規劃行程的使用者
- 上車地點（GPS）+ 目的地（手動輸入或快速選擇：家／公司／常用地點）
- 預估車資／車程
- 叫車完成後**不會**觸發任務／徽章／地圖點亮相關 UI

### 2.8 任務獎勵（取代原本的積分制）
- 完成任務（AI 規劃路線後叫車或訂位／每日推薦任務／節氣限定地點）後：
  - 解鎖對應**徽章**（節氣／季節限定條件才會有專屬徽章）
  - **地圖上點亮**造訪過的城市角落（視覺化的探索進度，非積分數字）
- 單純叫車、未完成任務的情境**不觸發**獎勵 UI

## 3. 明確移除／不要做的機制

- ❌ 每日積點／集點／連續打卡 Bonus（已於本輪對話中明確移除，改成徽章＋地圖點亮）
- ❌ 「斷一天積分歸零」邏輯
- ❌ 在使用者端呈現 OCR 介入畫面（OCR 是後端條件觸發，前端只需顯示最終可編輯結果）

## 4. 原型中「看起來真實、但其實是假資料／模擬」的部分

實作時這些都需要換成真實資料或真實串接：

| 項目 | 原型做法（假） | 正式應做法 |
|---|---|---|
| GPS 目前位置 | 寫死台南市東區座標 (22.9838, 120.2231) | 真實 Geolocation API |
| 收藏地點座標 | 5 筆寫死的真實地標經緯度 | 由 VLM/OCR 辨識結果 + geocoding API 產生 |
| VLM 圖片轉文字 | 無真實模型，2 秒後直接帶入寫死的示範資料 | 真實 VLM（如多模態模型）+ 條件觸發 OCR |
| AI 最佳路線排序 | 依假資料的 `dist` 欄位做簡單排序 | 真實路徑規劃／TSP 最佳化，或至少用真實距離矩陣 |
| 路線道路路徑 | OSRM 公開 Demo Server（僅供展示，正式環境需要自己的路徑規劃服務或商用 API） | 正式路徑規劃服務（有 SLA、有配額） |
| 叫車 / 餐廳訂位 | 純前端狀態切換，無真實下單 | 串接 yoxi 真實叫車後端 + 餐廳合作夥伴 API |
| 徽章 / 地圖點亮 | 寫死的示範文字與 emoji | 需要使用者資料持久化（帳號系統 + 資料庫） |
| 每日推薦任務 | 寫死單一任務內容 | 需要任務推播邏輯（依有空時段 + 偏好動態產生） |
| 十秒問答結果 | 只存在當前分頁的 JS 變數，重新整理就消失 | 需要持久化，並實際影響推薦演算法 |
| 使用者帳號 / 基本資料 | 無登入，資料只存在畫面上 | 需要帳號系統 |

## 5. 視覺設計系統（已定案，供沿用）

- **色彩基調**：仿舊車票紙質感，不是常見的「奶油白＋陶土紅」AI 預設配色
  - `--ink:#211C16`　`--paper:#F1E7CD`　`--paper-deep:#E3D4AC`　`--card:#FFFAF0`
  - `--red:#FF210C`（實際取樣自 yoxi logo 的品牌紅，非隨意選色）　`--red-deep:#C11207`
  - `--teal:#0E5C53`　`--mustard:#D89A2C`（徽章／badge 色）
- **字體**：Fraunces（serif，標題／品牌感）＋ Manrope（sans，內文）＋ IBM Plex Mono（**只用在真正的數字**：公里數、金額、時間、徽章數量——比照車票序號的質感，不是裝飾性標籤）
- **簽名視覺元素**：「想去的地方」卡片用撕票線＋缺角圓孔（呼應車票／收藏＝收集車票的產品概念），其餘地方刻意不重複使用這招，避免每個元件都長一樣
- **避免**：按鈕文字結尾加「→」的習慣（動詞本身講完整件事即可）、大量等寬字＋大寫字距的裝飾性標籤、外層近黑底＋亮色 eyebrow 的簡報式包裝
- Logo：品牌紅底＋白色逗號造型標誌（已內嵌於原型 onboarding 頁與 favicon）

## 6. 交付形式：網頁 App（PWA）

已定案走 PWA（單一 codebase、可加到手機桌面、最快上線）。以下提供**兩個技術棧選項**：
Option A 適合要接近正式上線品質的版本，Option B 是零成本、適合黑客松展示與快速 demo 的版本。
兩者都能達成 PWA，差別主要在後端與資料庫的成熟度。

### 6.1 Option A — Next.js + Vercel + Supabase（接近正式上線品質）

| 層 | 建議 | 理由 |
|---|---|---|
| 前端框架 | **Next.js**（App Router）+ TypeScript | 一個 repo 同時做前端頁面與 API routes，PWA 生態成熟，之後要轉原生也方便重用商業邏輯 |
| PWA 化 | `next-pwa` 或 `@serwist/next` | 產生 manifest.json + service worker，支援「加到主畫面」與基本離線快取 |
| UI／樣式 | Tailwind CSS | 原型的 design token（見第 5 節色彩／字體）可以直接對應成 Tailwind theme 設定 |
| 地圖 | 沿用 **Leaflet.js**，但底圖／路徑規劃建議換掉公開 Demo 服務 | OSM 公開圖磚 + `router.project-osrm.org` 只適合展示，正式環境沒有 SLA、會被限流；建議換成 Mapbox / MapTiler（圖磚）+ Mapbox Directions API 或自架 OSRM（路徑規劃） |
| 帳號 / 資料庫 | Supabase（Postgres + Auth + Storage 一次到位）或 Neon + NextAuth | 需要存：使用者基本資料、十秒問答歷史、收藏地點、徽章／地圖點亮進度 |
| 截圖上傳 + VLM 辨識 | Next.js API route 收檔案 → 存進 Supabase Storage / Cloudflare R2 → 呼叫多模態模型 API 做圖片轉文字 → 條件觸發 OCR | 對照第 2.4 節：前端只顯示「可編輯的最終結果」，OCR/VLM 全部在後端做，不要讓使用者看到中間過程 |
| 叫車 / 餐廳訂位 | 先用 mock API route 開發，介面定義好之後再串 yoxi 真實後端與餐廳合作夥伴 API | 對照第 2.6 節的兩條分支 |
| 部署 | Vercel | 跟 Next.js 是原生搭配，git push 自動部署，免費額度通常夠 demo／MVP 使用 |

### 6.2 Option B — GitHub Pages + Google Apps Script（零成本、適合黑客松展示）

| 層 | 建議 | 理由 |
|---|---|---|
| 前端框架 | **Vite + React**（SPA）或沿用原型的純 HTML/CSS/JS 寫法 | GitHub Pages 只能放靜態檔案，Next.js 的 SSR／API routes 在這裡用不到，改用純前端框架架構更單純 |
| PWA 化 | 手動寫 `manifest.json` + `service-worker.js`（vite-plugin-pwa 也可以） | GitHub Pages 天生就是 HTTPS，PWA 安裝條件已滿足 |
| 後端 | **Google Apps Script**（部署成 Web App，`doGet`/`doPost`） | 免費、免管理伺服器，可用 `UrlFetchApp` 呼叫外部 API（VLM、叫車、訂位） |
| 資料庫 | Google Sheets（透過 `SpreadsheetApp` 讀寫） | 黑客松展示資料量完全夠用，資料還能直接打開 Sheet 給評審看 |
| 帳號 | 黑客松展示階段可以先不做真登入（假 session）；要做的話另外接 Firebase Auth | GAS 沒有內建消費者導向的 auth 系統 |
| CORS 注意事項 | 前端 `fetch` 用 `Content-Type: text/plain` 送 POST（避開瀏覽器 preflight），GAS 端自己 `JSON.parse(e.postData.contents)`；回應用 `ContentService.createTextOutput(...).setMimeType(ContentService.MimeType.JSON)` | GAS Web App 對 CORS preflight 支援不完整，這是最常卡住的地方，一定要先驗證過 |
| 已知限制 | 單次執行上限 6 分鐘、每日執行時間／API 呼叫配額有限、Sheets 並發寫入容易鎖住 | 適合展示與低流量使用，**不適合**當作正式上線的長期架構，之後使用者變多要換掉這層 |

**怎麼選**：只是要在黑客松展示、評審打開連結玩一輪 → Option B，最快最省事。
如果比賽後還要繼續維運、接 yoxi 真實後端、預期有一定使用者量 → 直接用 Option A，
或是先用 Option B demo，得獎後再照 Option A 重建後端（前端 UI／design token 都可以留著沿用）。

### 6.3 交付方式

1. 把 `yoxi-app-flow.html` 和這份 `yoxi-PRODUCT-SPEC.md` 一起放進新專案的根目錄（例如 `/reference`）。
2. 在 Claude Code 裡開新專案，先跟它講清楚要走 Option A 還是 Option B，再下第一個 prompt，例如（以 Option A 為例）：

   > 我要用 Next.js（App Router + TypeScript + Tailwind）做一個 PWA，請先讀
   > `/reference/yoxi-PRODUCT-SPEC.md` 了解完整產品規格，`/reference/yoxi-app-flow.html`
   > 是畫面與互動行為的參考原型（不是要延用的架構，裡面全部是假資料跟 DOM 操作）。
   > 先照 spec 第 2 節的畫面清單，把所有畫面用 React 元件重新實作成可以本機跑起來的
   > 假資料版本，路由跟這個 App 的多畫面切換邏輯對應即可，不用一次做完整個後端。
   > UI 配色與字體照 spec 第 5 節設定成 Tailwind theme。

3. 假資料版本確認沒問題後，再依 spec 第 4 節的表格，一項一項換成真實串接
   （建議順序：帳號系統 → 收藏地點資料庫 → 地圖／路徑規劃換成正式服務 → VLM/OCR API → 叫車／訂位串接）。
4. 之後每次要新增/調整功能，都可以直接引用本文件的章節（例如「照 2.6 的出發與轉換分支」），
   Claude Code 才不會遺漏這次對話裡定案但沒寫進程式碼註解的決策。
